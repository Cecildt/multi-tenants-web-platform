# Proposal

## Why

`design-docs/architecture.md` says `astro-web-platform` calls the `tenants-graphql-api` GraphQL endpoints. Today it doesn't: `TenantsGrid.astro` and `tenants-actions.ts` import `tenants-db-lib` and query the D1 binding `DB` directly, so the admin UI and the database are tightly coupled and the API is bypassed. The Rust API is still an empty scaffold (`src/lib.rs` returns an empty 200), so there are no endpoints to call yet. This change builds the tenant GraphQL API and moves the Astro app onto it, so the API is the only component that talks to the database.

Adding and editing tenants are no-ops today (the actions only `console.log`). They become real mutations in this change.

## What Changes

- **New GraphQL API** in `tenants-graphql-api` (Rust, `async-graphql` on workers-rs) served at `POST /graphql`, backed by the D1 binding `DB`:
  - Queries: `tenants`, `tenant(tenantId)`.
  - Mutations: `createTenant`, `updateTenant`, `deleteTenant`.
  - Server-side input validation, server-generated tenant IDs, and ISO 8601 timestamps.
- **BREAKING (internal):** `astro-web-platform` no longer depends on `tenants-db-lib` or has a D1 binding. It reaches the API through a Cloudflare service binding `TENANTS_API`, with a `GRAPHQL_API_URL` fallback for local dev.
- A small server-only GraphQL client module in Astro (`src/lib/tenants-api.ts`) that the grid and the actions use. The browser never calls the API directly. Browser code keeps going through Astro Actions.
- `addTenant` and `editTenant` actions persist through the new mutations. `deleteTenant` and `getTenant` use the API. The edit page loads the tenant's current values.
- The tenant ID is generated by the API instead of by Astro's `nanoid`.
- The D1 migrate and seed scripts move from `astro-web-platform/package.json` to a new `tenants-graphql-api/package.json`, since the API now owns the database. `tenants-db-lib` stays as the source of the Drizzle schema and migrations.
- The API is not exposed on `workers.dev` in production until authentication exists. It's reached only through the service binding.
- Docs: `README.md`, `design-docs/deployment.md` (deploy the API before Astro), `design-docs/tech-stack.md` (async-graphql → In use), `design-docs/api-documentation.md` (replace the REST endpoint list with the GraphQL schema).

## Capabilities

### New Capabilities

- `tenants-graphql-api`: The GraphQL schema, endpoint, validation, and error behavior for querying and changing tenants in D1.
- `tenant-admin-ui`: How the Astro admin app lists, views, creates, edits, and deletes tenants, and the rule that it reaches tenant data only through the GraphQL API.

### Modified Capabilities

None. No specs exist yet under `openspec/specs/`.

## Impact

- **Code:** `tenants-graphql-api` (`src/lib.rs` plus new schema and resolver modules, `Cargo.toml`, `wrangler.toml`, new `package.json`); `astro-web-platform` (`wrangler.toml`, `package.json`, `src/actions/tenants-actions.ts`, `src/components/grids/TenantsGrid.astro`, `src/pages/tenants/[tenant_id].astro`, new `src/lib/tenants-api.ts`).
- **Dependencies:** Rust adds `async-graphql` (no default features), `serde`, `serde_json`, `uuid` (`v4`, `js`), and enables the `worker` crate's `d1` feature. Astro removes `tenants-db-lib`, `nanoid`, and `dotenv` (unused).
- **Infrastructure:** Astro's `wrangler.toml` swaps `[[d1_databases]]` for `[[services]]`. The API must be deployed before Astro, because a service binding to a Worker that doesn't exist fails to deploy.
- **Depends on:** `migrate-turso-to-d1`. Its remaining manual tasks (real `database_id`, local and remote migrate and seed) must be done before the verification steps here.
- **Out of scope:** authentication and authorization between Astro and the API; users and products; pagination; removing the now-unused runtime `DataStores`/`TenantsStore` from `tenants-db-lib`.
